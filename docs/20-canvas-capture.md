# 画布像素捕获与写回（实测，2026-11-21 22:20）

这一页只写**实际验证过**的事实。没验证的会明确标出「未验证」。

## 一、SAI 怎么把画布画到屏幕

在 `wintab32.dll` 里 hook `sai2.exe` 的 GDI IAT 之后观察到的调用分布：

| 调用 | 情况 |
|---|---|
| `BitBlt` | **0 次** |
| `StretchDIBits` | **0 次** |
| `CreateDIBSection` | 只有控件尺寸（如 231×259），没有画布 |
| `SetDIBitsToDevice` | **唯一**的绘制通道，画布、工具栏、面板全走它 |

画布那一次调用的形态（1600×1600 文档，50% / 75% / 100% 缩放都一样）：

```
SetDIBitsToDevice 800x800 at (180,73) start=0 lines=2560 bits=0x8D70000
  dst sflChildWindow "新建画布1 (50%)"
```

- 源 DIB：**3584×2560、32bpp、stride 14336、BI_RGB**
- `start=0`，`lines=2560` 覆盖整张 DIB
- 贴图目标：标题带 `(xx%)` 的画布子窗口

含义：**这张 DIB 是“屏幕空间（视口空间）”的合成缓冲**，不是文档缓冲。
一个 DIB 像素 = 一个屏幕像素；100% 缩放时才与文档像素 1:1。

用 `wt_canvas.bmp` 转储验证过内容正确（黑底 + 灰色画框 + 白色画纸 + 笔画）。

## 二、写回：能生效

探针在 `SetDIBitsToDevice` 返回前，往 DIB 中心写 320×320 品红（BGRA=FF00FFFF）：

- 转储出的 BMP 里出现品红方块 → **字节确实被改写**
- 屏幕上的画布直接显示品红 → **修改会随这次 blit 一起上屏**
- 反复触发重绘（多次 blit）、改缩放（100%→75%）之后**仍然在**

结论：SAI **不是每帧从图层重新合成**，只重绘脏区；只要它不认为那块脏，写进去的像素就一直留在画面上。

## 三、还没定的：这算不算“文档内容”

写进 DIB 的像素会不会：

1. 被“另存为”写进文件？
2. 被撤销/重做、画笔落笔等文档级操作冲掉？
3. 被复制/滤镜等内部读取操作读到？

这三条决定架构，**必须先验证第 1 条**（另存为 PNG 后读回来看像素）。
验证方法：写品红 → 文件→另存为 `C:\users\xuser\save1.png` → 拉回来看。

## 四、图层像素不在这块缓冲里（已验证）

在画布有内容（1600×1600 渐变图 + 笔画）时，从 DIB 取一段 64 像素宽、变化最剧烈的
特征串（256 字节），扫描整个进程的可读私有内存：

```
done: 237 regions (135 >=4MB), 1 hits
HIT 0x96BD2A0 region=0x8D70000 size=35840 KB
```

唯一命中就是 DIB 自己（`0x8D70000` 正是 `bits`）。

也就是说：**图层像素不是以「和屏幕一致的 32bpp 平铺」形式存在的**。
可能原因（均未验证）：分块 tile 存储、每通道 16 位、预乘 alpha、压缩/量化的历史数据、
或者干脆是 SAI 自己的图块格式。

进程里只有 3 个超过 4MB 的私有可写区域：9MB ×1、35MB ×2（其中一个是 DIB）。
1600×1600×4 = 10.24MB，没有对应的区域 → 更说明不是裸的 32bpp。

## 五、探针的接口（`liquify/probe/wintab32_probe.c`）

在 `wintab32.dll` 里加一整套**纯内存、触发式**的开发探针。**热路径绝不写文件**——
早期版本在 `SetDIBitsToDevice` 里直接 `fflush`，笔画期间把 SAI 拖死到整机 ANR。

| 开关文件（相对 `drive_c`） | 作用 |
|---|---|
| `wt_canvas_capture` | 加载时安装 GDI IAT hook（存在才装） |
| `wt_write` | 下一次画布 blit 时往 DIB 写 320×320 品红，落盘 BMP + 日志 |
| `wt_memscan` | 从下一次画布 blit 取特征串，扫描全进程私有内存 |
| `wt_pattern.bin` + `wt_memscan` | 用指定字节串做模式搜索（判定像素格式用） |
| `wt_dump.txt`（内容 `"<hexaddr> <len>"`） | 转储任意内存区域到 `wt_dump.bin` |

输出：`wt_gdi.log`、`wt_canvas.bmp`、`wt_memscan.log`、`wt_dump.bin`。

### 部署注意（踩过的坑）

- APK 内置了 DLL：`PenBridge.ensureBridgeFiles()` 在启动容器时按 **文件长度** 判断是否覆盖。
  调试版必须把 DLL 补齐到**正好 94720 字节**（补 0 即可），否则一启动就被换回发行版。

  `AppData/Local/SYSTEMAX Software Development/SAIv2/hisdata/<时间戳>.N/`。

## 六、液化引擎（`liquify/engine/`）

与捕获/写回解耦的纯 C99 引擎，同一份代码要能编进 Wine DLL，也能在 Mac 上跑单测。

模型：**逆位移场 + 分块重建**

- 一笔开始时复制整面（这份拷贝同时是 undo 源和重采样源）
- 每个笔刷步只累加逆位移场（`int16`，1/16 像素，按 64×64 tile 惰性分配）
- `lq_flush()` 只重建脏 tile，对同一份位移场**幂等**
- 平滑是破坏性的（没有位移可表达），所以同步更新拷贝

实测（M 系列 Mac，单线程）：

```
forward dirty bbox 83,119 .. 241,201
changed=8389  changed_outside_100px=0
idempotent=1
undo_restores=1
big canvas 3584x2560: stroke_begin + 40 steps + flush = 18.2 ms
```

六种模式：`forward / bloat / pinch / twirl_cw / twirl_ccw / smooth`。

## 七、图层像素在哪里（2026-11-21 23:00 追加）

### 一个关键错误假设：alpha 是 0

画布像素的 alpha 通道是 **0**，不是 255。所有按 `BGRA=..FF` 去搜的模式全部漏掉，
这也是第一次“纯色反查”一无所获的原因。用 `00 00 FF 00`（BGR + alpha=0）立刻命中。

### 内存里确实有像素，但只有两种形态

| 形态 | 特征 | 位置 |
|---|---|---|
| 视口缓冲 | 行 stride **14336**（= 3584×4），红色连续 512 px 一段 | `0x8D70000`（呈现给屏幕的那张 DIB）、`0xB070000`，以及若干 4MB 块 |
| 小块/瓦片 | 行 stride **1024**，每段 32 px（128 B） | `0x12290000` 一带 |

`/proc/<pid>/maps` 里 `0x12260000–0x12BF0000 rw-p` 是一块 **10,027,008 字节**的匿名映射，
大小接近 1600×1600×4 = 10,240,000，一度以为是图层缓冲；逐块抽样后是
「开头一小片红/白 + 其余全 0」，**不是**一张图，更像索引/哈希表一类的结构。

`0.0.0.t.dat` 被 `rw-s` 映射在 `0x12230000–0x12255000`（148 KB），是共享文件映射。

### 文档存储是压缩的

当前会话 `hisdata/20261121.142249.2/`：

```
0.0.0.t.dat   147568 B   固定大小，与画布尺寸无关 → 索引
2.0.0.t.dat    65648 B   1600×1600 纯红画布 → 0.026 B/px，必然是压缩/编码
2.0.0.a.tmp     4096 B
Info.dat        1024 B
```

### 尚未解决

**没有找到「文档分辨率、可直接写、SAI 会当作文档数据」的像素缓冲。**

已排除的候选：

- 裸 32bpp 平铺（1600×1600×4 = 10.24 MB，块级搜索无命中）
- 16 位/通道、RGB565、24bpp 打包、预乘（全部无命中）
- 10 MB 匿名映射（内容是索引，不是图）
- 视口 DIB（写进去只上屏，另存 PNG 里 0 像素）

剩下两条可能（都未验证）：

1. 图层被切成 32 px 行、stride 1024 的小块结构，需要先逆出块头/索引关系
2. 图层只在「解码 → 合成 → 编码」的瞬间以裸像素出现在临时缓冲里，永不常驻

如果是第 2 种，直接改内存这条路走不通，只能改成**挂钩子**：
在 SAI 解码出瓦片之后、合成之前把像素改掉，并且在编码回去之前再改一次——
这样每次存盘、每次重绘都会带我们的结果，等价于文档真的被改了。
代价是要逆出 SAI 的瓦片编解码入口。

## 八、B 路线的侦察结果（2026-11-21 23:25）

### sai2.exe 的 GDI 面很小

`llvm-objdump -p sai2.exe` 拿到 GDI32 导入表，关键事实：

| 函数 | 导入 | 实测调用 |
|---|---|---|
| `SetDIBitsToDevice` | 是 | 唯一绘制通道，画布走它 |
| `CreateDIBSection` | 是 | 画布/控件表面 |
| `BitBlt` | 是 | **hook 期间 0 次** |
| `StretchDIBits` / `StretchBlt` / `SetDIBits` / `PatBlt` | **未导入** | — |

结论：**画布 DIB 的像素是 SAI 自己的代码直接写内存填的**，不是靠 GDI 搬。
所以「挂钩子找合成入口」只能走「监控谁写了这块内存」，不能靠扩展 GDI hook 列表。

### 两个否定的侦察

1. **PAGE_GUARD + VEH 没抓到**
   给 DIB 中心 16 页装 `PAGE_GUARD`，注册 `AddVectoredExceptionHandler`，
   用户落笔、强制 invalidate 之后一条 `WATCH` 命中都没有。
   可能是 Wine/Box64 的异常路径没走到 VEH，也可能是守错了页。
   控制实验也没能证明机制本身可用（poke 命令自己会先 `VirtualProtect` 解锁，测不出来）。
   **结论：这条监控手段尚未验证，不要当成已成立。**

2. **`PivInk.dll` 是壳，不是引擎**
   `sai2.exe` 只从它导入 `UuidCreate`，它自己也只导出 `UuidCreate`。
   621 KB 的 `.text` 里没有对外 API。画布引擎在 `sai2.exe`（5.2 MB，`.text` ≈ 4 MB）里。

### B 的具体落点（下一步）

目标是找到「SAI 把解码后的瓦片写进画布 DIB」那一条路径，在它之前插一手。三条可行做法，按代价排序：

1. **静态定位 `SetDIBitsToDevice` 的调用者**
   IAT 槽位已知，反查 `call [iat]` → 找到呈现函数 → 它的上游就是合成函数。
   有了合成函数，顺着它读的缓冲区就能找到「解码输出」。
   纯静态、可离线做，是当前最稳的入口。

2. **换一种监控手段**
   不用 PAGE_GUARD，改成把画布 DIB 的目标地址换掉：hook `CreateDIBSection`，
   把返回的 bits 换成我们自己分配的一块，并在尾部加影子页；
   或者用 `mincore`/周期抽样差分来定位写入窗口。

3. **从编码侧倒推**
   `hisdata/*.t.dat` 每次编辑都会重写。hook `WriteFile` 抓写入缓冲，
   拿到的是编码后的字节流；对它做差分/熵分析可以反推瓦片尺寸和编码方式。
   注意 `2.0.0.t.dat` 在 512×512 和 1600×1600 两种画布下**都是 65,648 字节**，
   说明它是**定长索引/表**，不是像素本体。

### 已知的确定性结论（这些不用再试）

- 视口 DIB 可读写、能上屏、同视图下能留存，但**不进文档**（另存 PNG 里 0 像素）
- 画布像素 alpha 通道是 **0**
- 文档分辨率下**没有**裸 32bpp / 24bpp / 16bpp / 565 的平铺缓冲
- `hisdata/2.0.0.t.dat` 与画布尺寸无关 → 定长表

## 九、静态定位入口（2026-11-21 23:30，可直接接着做）

`sai2.exe` 是 PE32+，`ImageBase = 0x140000000`，`.text` 从 `0x140001000` 开始。
用脚本解析导入描述符拿到的 **GDI32 IAT 槽位**（运行时地址，非 RVA）：

| 函数 | IAT 地址 |
|---|---|
| `BitBlt` | `0x14035b0a8` |
| `CreateDIBSection` | `0x14035b0b8` |
| `ExtTextOutW` | `0x14035b0f0` |
| `CreateDIBitmap` | `0x14035b140` |
| `SetDIBitsToDevice` | `0x14035b158` |

**调用点只有 3 处**，全部落在同一个函数里（呈现函数）：

```
0x14025326c   callq *0x107ee6(%rip)   # SetDIBitsToDevice
0x140253374   callq *0x107dde(%rip)   # SetDIBitsToDevice
0x1402534a2   callq *0x107cb0(%rip)   # SetDIBitsToDevice
```

调用约定（x64 第 9 个参数是 `lpvBits`）：`bits` 从 **`[rbp+0x18]`** 取，
另有 `[rbp+0x20]`、`[rbp+0x28]` 分别喂 `bmi` 与另一个分支，说明 `rbp` 指向一个
「画布视图 / 表面」对象。

### 下一步（按顺序）

1. 定位这个呈现函数的起始地址（从 `0x14025326c` 往前找 `sub rsp` / `push` 序言）。
2. 反查谁调用它 → 得到「合成完成 → 呈现」的调用点；那个调用者的上一环就是合成器。
3. 顺着 `[rbp+0x18]` 的对象结构，找出 DIB 指针的赋值点 —— 那里就是「谁把像素写进画布 DIB」。
4. 合成器一旦定位，它读的缓冲区就是解码后的瓦片；在那里插钩子（B 的目标）。

第 3 步尤其关键：**找到「写入 DIB 指针」的那条指令**，比抓内存写更省事，
而且完全离线可做，不需要设备。

### 画布表面的创建点（离线定位，2026-11-21 23:40）

`CreateDIBSection` 在整个 `sai2.exe` 里**只有 1 个调用点**：`0x140255350`。
它前面的代码把结构体字段串起来，得到「表面对象」的布局：

```
1402552f3  leal 0x8(%rbx), %edx        ; 尺寸派生
1402552f9  call [0x14035b0c8]
140255305  movq %rax, 0x18(%rdi)       ; +0x18 = 像素指针（ppvBits 出参落点）
14025530f  movq %rax, 0x28(%rdi)       ; +0x28 = 另一份/掩码
140255331  movq 0x28(%rbp), %rdx       ; rdx = BITMAPINFO（宽高在这里）
140255335  leaq 0x18(%rbp), %r9        ; r9  = &bits（本地）
140255350  call CreateDIBSection       ; <-- 唯一调用点
140255356  movq %rax, 0x10(%rdi)       ; +0x10 = HBITMAP
```

结论：**表面对象布局 = `+0x10` HBITMAP / `+0x18` 像素指针 / `+0x28` 掩码或副表**，
宽高来自 `+0x28` 处的 `BITMAPINFO`。
这和呈现函数里 `movq 0x18(%rbp), %r8`（第 9 个参数 lpvBits）**完全对上**。

   但必须**先按 BeginAddress 排序再去重**，并且只取 `BeginAddress != 0` 的项。
2. 用修正后的边界反查 `0x1402552d9` 外层函数的直接调用者 → 找到「新建画布/打开文档」时建立表面的地方。
